# 실측 기록

기획안이 "실측 후 결정"으로 남긴 항목들을 이 환경에서 측정한 결과.
**하드웨어가 다르면 숫자도 다르다.** 자기 장비에서 `aicut benchmark <원본>`으로 다시 재라.

측정 환경: 컨테이너, CPU만(GPU 없음), ffmpeg 7.1.1, OpenCV 4.14.

## R3 — 처리 시간

30분 원본(854x480, 15fps, 223MB) 신호 추출:

| 단계 | 시간 |
|---|---|
| 무음 검출 | 12.9s |
| 라우드니스 엔벨로프 | 14.2s |
| 화면 변화 | 12.1s |
| 프레임 샘플링(5초 간격) | 7.4s |
| 얼굴 검출(360프레임) | 4.8s |
| **합계** | **51.4s** |

- 실시간 대비 **35배속**
- 6시간 원본 외삽: **신호 추출 약 10분**

30분 원본 전체 파이프라인(mock 추론 + 렌더 2편): **89초**.

**여기 STT와 추론 호출은 빠져 있다.** 실제 운용에서는 그 둘이 지배적이다.
WhisperX large-v3는 GPU가 필요하고 이 환경에서 측정 불가 — 20.2가 요구하는
"6시간 원본의 STT + 비전 분석 처리 시간"은 실제 GPU에서 재야 한다.
1차 통과 밀도(`scan.pass1_window_sec`)가 추론 호출 수를 직접 결정하므로,
비용의 지배 변수는 거기다.

## 10.4-1 — 줌 전략

| 전략 | 결과 |
|---|---|
| `segment_crop` | 동작. 구간별 고정 크롭 + concat. 계단식 카메라 |
| `sendcmd` | **팬만 가능.** crop `w`/`h`를 런타임에 바꾸면 필터 그래프 교착 |

sendcmd로 crop 크기 변경 시: 벽시계 60초, CPU 0.5초, 출력 0바이트 — 도는 게
아니라 멈춤. 하류 scale 필터가 재구성을 안 한다. x/y만 보내면 같은 구간 0.67초.

따라서 **배율이 변하는 줌은 `segment_crop`**, 고정 배율 팬은 sendcmd.
MVP 6의 (a)/(b) 비교에서 (b)는 "부드럽지만 팬 전용"으로 확정.

## OpenCV 버전 문제

OpenCV 5.0이 `CascadeClassifier`를 **제거**했다. `pip install opencv-python`이
5.x를 설치하면 얼굴 신호가 조용히 사라진다(경고는 찍힘, 라벨은 UNKNOWN).

대응: 두 백엔드 지원.
- OpenCV ≥4.5.4 + YuNet `.onnx` 모델(`AICUT_FACE_MODEL` 환경변수) → DNN 검출
- OpenCV 4.x → 번들 Haar cascade

둘 다 없으면 `build_detector()`가 `None`을 돌려주고 5.3 라벨은 UNKNOWN으로 남는다.

## 입력 검증

| 입력 | 처리 |
|---|---|
| 없는 파일 / 0바이트 / 쓰레기 | `UnusableSource` — 입력 문제로 분류 (렌더 오류 아님) |
| 오디오 없음 | 거부. 5.2가 소리를 전제 |
| 비디오 없음 | 거부 |
| **잘린 파일** | 경고 후 진행. 컨테이너는 원래 길이를 계속 주장한다 |

잘린 Matroska는 헤더가 멀쩡해서 duration을 60초로 보고하지만 실제 패킷은
19.5초에서 끊긴다. 게다가 ffmpeg는 `File ended prematurely`를 찍고도 **exit 0**.
그래서 끝부분 프레임을 실제로 뽑아 파일이 생겼는지 확인한다. 그게 유일한 신호다.
