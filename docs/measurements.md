# 실측 기록

기획안이 "실측 후 결정"으로 남긴 항목들을 이 환경에서 측정한 결과.
**하드웨어가 다르면 숫자도 다르다.** 자기 장비에서 `aicut benchmark <원본>`으로 다시 재라.

측정 환경: 컨테이너, CPU만(GPU 없음), ffmpeg 7.1.1, OpenCV 4.14.

## R3 — 처리 시간

30분 원본(854x480, 15fps, 223MB) 신호 추출:

| 단계 | 시간 |
|---|---|
| 무음 검출 | 12.9s |
| 라우드니스 엔벨로프 | 14.2s |
| 화면 변화 | 12.1s |
| 프레임 샘플링(5초 간격) | 7.4s |
| 얼굴 검출(360프레임) | 4.8s |
| **합계** | **51.4s** |

- 실시간 대비 **35배속**
- ~~6시간 원본 외삽: 신호 추출 약 10분~~ — **외삽하지 않고 실제로 쟀다. 아래 참조.**

30분 원본 전체 파이프라인(mock 추론 + 렌더 2편): **89초**.

**여기 STT와 추론 호출은 빠져 있다.** 실제 운용에서는 그 둘이 지배적이다.
WhisperX large-v3는 GPU가 필요하고 이 환경에서 측정 불가 — 20.2가 요구하는
"6시간 원본의 STT + 비전 분석 처리 시간"은 실제 GPU에서 재야 한다.
1차 통과 밀도(`scan.pass1_window_sec`)가 추론 호출 수를 직접 결정하므로,
비용의 지배 변수는 거기다.

## 10.4-1 — 줌 전략

| 전략 | 결과 |
|---|---|
| `segment_crop` | 동작. 구간별 고정 크롭 + concat. 계단식 카메라 |
| `sendcmd` | **팬만 가능.** crop `w`/`h`를 런타임에 바꾸면 필터 그래프 교착 |

sendcmd로 crop 크기 변경 시: 벽시계 60초, CPU 0.5초, 출력 0바이트 — 도는 게
아니라 멈춤. 하류 scale 필터가 재구성을 안 한다. x/y만 보내면 같은 구간 0.67초.

따라서 **배율이 변하는 줌은 `segment_crop`**, 고정 배율 팬은 sendcmd.
MVP 6의 (a)/(b) 비교에서 (b)는 "부드럽지만 팬 전용"으로 확정.

## OpenCV 버전 문제

OpenCV 5.0이 `CascadeClassifier`를 **제거**했다. `pip install opencv-python`이
5.x를 설치하면 얼굴 신호가 조용히 사라진다(경고는 찍힘, 라벨은 UNKNOWN).

대응: 두 백엔드 지원.
- OpenCV ≥4.5.4 + YuNet `.onnx` 모델(`AICUT_FACE_MODEL` 환경변수) → DNN 검출
- OpenCV 4.x → 번들 Haar cascade

둘 다 없으면 `build_detector()`가 `None`을 돌려주고 5.3 라벨은 UNKNOWN으로 남는다.

## 6시간 규모 — 메모리와 IO

기획안이 처리 시간(R3)만 위험으로 적었고 메모리는 아무도 재지 않았다. 6시간
방송이 만들어내는 신호를 실제 크기로 만들어 통과시킨 결과:

| 항목 | 값 |
|---|---|
| RMS 프레임 | 21,600 (1초 간격) |
| 화면 변화 샘플 | 4,320 (5초 간격) |
| 발화 | 4,950 / 단어 39,600 |
| 텐션 곡선 생성 | 0.1초 |
| 버스트 검출 | 0.0초 |
| 신호 캐시 파일 | 0.9 MB (저장 0.1초 / 로드 0.0초) |
| 창 단위 발화 조회 | 0.00초 (인덱스 적중) |
| **최대 RSS** | **56 MB** |

데스크톱 프로그램(22.1)으로 감당 가능한 규모다. 1차 통과의 추론 호출이 비용을
지배하고 신호 보관은 문제가 아니다.

## 6시간 원본 — 외삽이 아니라 실측

30분 원본에서 외삽한 "약 10분"을 실제 6시간 파일로 대체했다. 6시간짜리
방송(21,600초, 320x180, 10fps, 370MB)을 만들어 파이프라인에 통째로 넣었다.

`aicut benchmark`, 신호 추출:

| 단계 | 시간 |
|---|---|
| 무음 검출 | 133.7s |
| 라우드니스 엔벨로프 | 140.9s |
| 화면 변화 | 123.9s |
| **합계** | **398.5s (6.6분)** |

**실시간 대비 54배속.** 무음 18개, 라우드니스 프레임 19,846개, 화면 변화
샘플 4,320개. 외삽값(10분)보다 빠른데, 이 원본이 320x180이라 화면 변화
패스가 유리하다. 해상도가 올라가면 그 항목부터 늘어난다.

전체 파이프라인, 편집 계획까지(발화 4,976개, mock 추론, `--no-render`):

| 항목 | 값 |
|---|---|
| 벽시계 | 254s (4.2분) — 실시간 대비 **85배** |
| 최대 RSS | 74 MB |
| 1차/2차 창 | 181 / 181 |
| 사건 · 후보 | 3 · 3 |
| 판정 | produce 1 / combine 2 / hold 0 / reject 0 |
| 계획된 에피소드 | 1편 (컷 179개, 16,195초, 가장 긴 컷 90.5초, 자막 3,758줄) |
| 데이터베이스 | 5.6 MB |

`--no-render`는 프로젝트를 PLANNING에 남긴다. 중간 상태로 남기는 게 맞다 —
`aicut resume`가 이어받는다 (16장).

주의: **이 시스템이 "에피소드 1편"이라 부른 것은 4.5시간짜리다.** mock 추론이
언급 하나당 비트 하나를 만들고 고르지 않기 때문이고, mock 스스로 그렇게 적는다
(`"mock: length taken from the mentions, not from the user's hint"`). 실제 추론
백엔드는 고른다. 길이는 결정이지 상수가 아니므로(2.6) 여기에 상한을 두지 않았다.

**이 실행이 진짜 버그를 하나 잡았다** — 짧은 픽스처로는 절대 나올 수 없는
종류다. 장면 길이 상한이 없어서 6시간 발화 전체가 장면 하나가 됐고, 그
결과 편집 계획이 컷 179개 / 원본 3,830,063초(44일) / 자막 828,949줄로
나왔다. 원인과 수정은 커밋 `fbd92ff`. 고친 뒤 같은 원본의 계획:

| | 수정 전 | 수정 후 |
|---|---|---|
| 컷 총 원본 길이 | 3,830,063s | 16,195s |
| 가장 긴 컷 | 21,397s | 90.5s |
| 자막 | 828,949줄 | 3,758줄 |

## 렌더 비용 — 원본 길이가 아니라 결과물 길이에 비례

6시간 원본에서 뽑은 9분짜리 에피소드를 실제로 렌더한 결과:

| 항목 | 값 |
|---|---|
| 컷 6개 / 결과물 539초 | 6시간 중 357분에 걸쳐 흩어진 지점들 |
| 렌더 벽시계 | 82s (결과물 기준 **6.5배속**) |
| 결과물 | 76.2 MB |
| 최대 RSS(파이썬) | 18 MB — ffmpeg는 별도 프로세스 |
| 렌더 후 작업 디렉터리 | **0 MB** (성공 시 정리됨) |

구간 잘라내기만 따로 재면 **결과물 기준 12.3배속, 초당 1.8 MB 기록**.
6시간 컨테이너를 컷마다 새로 seek하는데도 그렇다 — 렌더 비용을 지배하는
것은 원본 길이가 아니라 만들려는 영상 길이다.

**실패한 렌더는 구간 파일을 남긴다.** 4.5시간짜리 계획을 렌더하던 중
측정한 값으로 작업 디렉터리가 1.4 GB까지 갔다. 일부러 남기는 것(원인을
보려면 그게 필요하다)이지만 어느 디렉터리인지 로그에 찍는다. 성공하면 지운다.

## ffmpeg 빌드 차이 — libass 없는 ffmpeg

macOS CI가 `brew install ffmpeg` 직후 자막 렌더에서 죽었다:

    [AVFilterGraph] No such filter: 'subtitles'
    Error opening output files: Filter not found

Homebrew가 formula를 쪼갰다. 지금 `ffmpeg` 병에 딸려오는 의존성은 11개
(dav1d·lame·libvpx·opus·x264·x265 등)이고 **libass가 없다.** libass가 없으면
`subtitles`·`ass` 필터 자체가 존재하지 않는다. macOS에서 가장 흔한 설치
방법이 곧 자막을 태울 수 없는 ffmpeg라는 뜻이다. CI 사정이 아니라 사용자
환경이다.

| 빌드 | 필터 수 | `subtitles` |
|---|---|---|
| Debian `ffmpeg` 7.1.1 | 434 | 있음 |
| Homebrew `ffmpeg` 8.1.2 | — | **없음** |
| Homebrew `ffmpeg-full` | — | 있음 |

대응은 세 겹:

1. `available_filters()`가 `ffmpeg -filters`를 읽어 빌드가 실제로 뭘 할 수
   있는지 묻는다. 가정하지 않는다. — **이 파서를 처음 쓸 때 틀렸다.** 플래그
   열이 알파벳이 아닌 것으로 필터 줄을 골랐는데, 플래그가 `TSC`(타임라인·슬라이스·
   커맨드 전부 지원)인 필터 121개가 통째로 빠졌다: `overlay`, `blend`, `rotate`,
   `lut3d`... 안 보이는 게 아니라 **없다고 보고**하므로, `require_filter`가
   멀쩡한 빌드에서 렌더를 거부했을 것이다. 지금은 `^ [TSC.]{3} 이름 in->out`로
   맞춘다. 555개 전부, ffmpeg가 나열한 것과 정확히 일치하는지 테스트가 잡는다.
2. `Renderer.render`가 **자르기 전에** 확인한다. 다 만들어 놓고 마지막
   명령에서 죽으면 원인이 안 보인다.
3. 파이프라인은 에피소드를 버리지 않는다. 자막 없이 렌더하고 `.ass`는 옆에
   남기고, 이탈을 report와 에피소드 메모에 적는다 (2.6 — 조용한 이탈 금지).
   libass 있는 빌드를 깔고 렌더만 다시 돌리면 자막이 붙는다 (16장).

`aicut doctor`가 이제 필터 가용성을 같이 찍는다. 6시간 돌린 뒤에 알 일이 아니다.

검증: `subtitles`·`ass` 필터를 제거한 가짜 ffmpeg를 PATH에 앞세워 전체 스위트를
돌렸다 — 301개 통과, 자막 번인 검사 2개만 건너뜀.

## STT — 실제 인식기

이전까지 STT는 트랜스크립트 파일로만 검증했다. 즉 **인식기 출력이 실제로 이
시스템이 쓸 수 있는 모양인지는 확인한 적이 없었다.** PocketSphinx는 음향
모델을 패키지 안에 싣고 오므로 네트워크도 GPU도 없이 돌아간다. espeak-ng로
말을 만들고 그걸 인식시켜 파이프라인 전체를 통과시켰다.

문장 3개, 사이에 4초 침묵:

| 항목 | 값 |
|---|---|
| 오디오 | 24.9s |
| 인식 시간 | 5.3s (**4.7배속**, CPU) |
| 단어 | 37개 발화 / 29개 인식 |
| 발화 묶음 | **3개** (침묵 3개가 경계 3개로) |

인식 정확도는 나쁘다("i am very nervous about this match"가 "i really good
about it"으로 나온다). 그게 요점이 아니다. 요점은 단어 타임스탬프와 침묵
경계가 세그먼트 층이 쓸 수 있는 형태로 나온다는 것이고, 그건 확인됐다.

WhisperX large-v3의 6시간 처리 시간(20.2)은 여전히 GPU에서 재야 한다.

## 배포 형태

`python -m build` 산출물 둘 다 필요한 파일을 싣는다: sdist·wheel 모두
`aicut/resources/profiles/default.json`, `aicut/resources/subtitle_styles/default.json`,
`aicut/db/schema.sql`, `aicut/ui/static/index.html` 포함. 설치본을 저장소 밖
디렉터리에서 실행해 렌더와 UI까지 확인했다.

한글·공백·대괄호가 섞인 경로(`한글 폴더 (test)/방송_2026-08-19 [하이라이트].mkv`)에서
파이프라인 전체가 돌고 자막도 정상 번인된다(자막 구간 PSNR 7.0).

## 입력 검증

| 입력 | 처리 |
|---|---|
| 없는 파일 / 0바이트 / 쓰레기 | `UnusableSource` — 입력 문제로 분류 (렌더 오류 아님) |
| 오디오 없음 | 거부. 5.2가 소리를 전제 |
| 비디오 없음 | 거부 |
| **잘린 파일** | 경고 후 진행. 컨테이너는 원래 길이를 계속 주장한다 |

잘린 Matroska는 헤더가 멀쩡해서 duration을 60초로 보고하지만 실제 패킷은
19.5초에서 끊긴다. 게다가 ffmpeg는 `File ended prematurely`를 찍고도 **exit 0**.
그래서 끝부분 프레임을 실제로 뽑아 파일이 생겼는지 확인한다. 그게 유일한 신호다.
